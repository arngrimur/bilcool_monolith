# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

### Primary task runner (Taskfile.yml)

```bash
task up                         # minikube: start, build + load all images, helm install with values-dev.yaml + values-secrets.yaml (infrastructure/helm)
task down                       # helm uninstall (keeps the DB volume); task down:purge also removes Postgres, secrets and the volume
task minikube:port-forward      # UI :3000, Postgres :54320, LocalStack :4566
task test-all                   # Run all unit + integration tests across every module
task swagger                    # Regenerate Swagger/OpenAPI docs (bookings and event_ledger only)
task vendor                     # Generate go.work (all modules incl. bilcool-lib) and vendor them
task coverage-all               # Generate merged HTML coverage report in /tmp/coverage/
task lambda-build-all           # Build every Lambda zip (provided.al2023, arm64)
task bookings_db                # psql into the local bookings database
```

> `task up` needs `infrastructure/helm/values-secrets.yaml` (gitignored; `cp infrastructure/helm/values-secrets.example.yaml ...`). Dev uses `MAIL_SENDER=log`: the login code is written to the authentication pod log (`kubectl logs deploy/authentication | grep "security token"`), no Brevo account needed. See `infrastructure/helm/README.md`.

Per-service tasks follow the pattern `<service>:<action>`:

```bash
task bookings:build            # also: bookings:test, bookings:integration-test, bookings:lambda-build
task authentication:build      # also: :test, :integration-test, :lambda-build
task journal:build             # also: :test, :integration-test, :lambda-build
task event_ledger:build        # also: :test, :integration-test, :lambda-build
task message_broker:build      # also: :test, :integration-test
task bilcool-lib:build         # also: :test
task testing:build

task ui:build
task ui:test
task ui:dev                     # Vite dev server on :3000
```

Minikube / Helm helpers: `minikube:build`, `minikube:build-<service>`, `minikube:build-migrate[-<service>]`, `minikube:helm-upgrade`, `minikube:port-forward`, `minikube:kill-port-forward`. Run `task --list` for the full, current list.

### Direct Go commands (run from the relevant module directory)

```bash
go build ./...                  # Build all packages
go test ./...                   # Run unit tests
go test -tags=integration ./... # Run integration tests (require Docker/testcontainers)
go generate ./...               # Regenerate mocks before running tests
go vet ./...                    # Static analysis
```

> **Important**: Always run `go generate ./...` before `go test` — tests depend on generated mocks.
>
> `go.work` and `vendor/` are gitignored and do not exist in a fresh clone. Run `task vendor` first.

### Database (local)

```bash
task up                                              # Helm starts Postgres, runs db-init + the migrations
task bookings_db                                     # psql as the bookings role (schema bookings)
```

Migrations are managed with [dbmate](https://github.com/amacneil/dbmate). Migration files live under `<service>/internal/migrations/` (bookings, authentication, journal; event_ledger uses DynamoDB and has none). The Helm chart runs them as one `migrate-<service>` Job per service (pre-install/pre-upgrade hook) from the `Dockerfile.migrate` image of each service.

## Repository layout

This is a **Go multi-module workspace**. Each service is its own Go module with its own `go.mod`; the workspace file `go.work` is generated by `task vendor`.

```
bilcool_monolith/
├── go.mod                  # Root module (swaggo/swag, Swagger generation)
├── Taskfile.yml            # Build / test orchestration (taskfile.dev)
├── plan.md                 # Neon -> Frostmoln database migration plan and progress log
├── docs/                   # Generated Swagger/OpenAPI definitions
├── .github/workflows/      # build.yml (CI/CD), fetch-logs.yml (CloudWatch logs, manual)
│
├── bookings/               # Bookings service
├── authentication/         # Authentication service
├── event_ledger/           # Event Ledger service (DynamoDB)
├── journal/                # Journal service
├── message_broker/         # Shared outbox/inbox library (not a running service)
├── bilcool-lib/            # Shared logging + HTTP middleware (correlation id)
├── testing/                # Shared test helpers (testdb, aws/local_cloud)
├── ui/bilcool-ui/          # React + TypeScript SPA (Vite)
│
└── infrastructure/
    ├── helm/bilcool/       # Helm chart (Kubernetes)
    ├── frostmoln/          # Frostmoln Terraform (VPC, Postgres, load balancer) + bootstrap scripts
    └── production/         # AWS production: terraform/ (Lambdas, SNS/SQS, DynamoDB, CloudFront/S3), bootstrap/ (state bucket), kubernetes/ (legacy), PLAN.md (historical)
```

The nested `internal/` ensures service internals cannot be imported by other services, enforcing service boundary isolation even within the monolith. Only types under `pkg/` (no `internal`) are intentionally exported.

## Architecture

BilCool is a booking application built as a monolith structured for future extraction into microservices. Services talk to each other through events (SNS/SQS); gRPC is a possible future step and is not used today. All HTTP APIs are REST (Gin).

### Where it runs

| Target | Used for | How |
|---|---|---|
| **AWS Lambda** | **Production (today)** | `cmd/lambda/*` entrypoints, Terraform in `infrastructure/production/terraform`, CI `lambda-deploy` |
| Kubernetes (Helm, minikube) | Local development | `infrastructure/helm`, `task up` |
| Kubernetes (Helm) | Minikube, and later Frostmoln | `infrastructure/helm/bilcool`; the CI deploy to Frostmoln is switched off by default |

Production in detail: Lambdas are exposed through Lambda Function URLs behind CloudFront (the SPA comes from S3, `/api/v1/...` paths go to the Function URLs). Events flow over SNS topics and SQS queues. The outbox is published by scheduled Lambdas (`OUTBOX_MODE=polling`). The site is `bilcool.areskiftet44.se`, DNS is edited by hand at Loopia, and mail is sent through Brevo.

Lambda entrypoints (`<service>/cmd/lambda/`): bookings `http, sqs, outbox, migrate`; authentication `http, outbox, migrate`; journal `http, sqs, migrate`; event_ledger `http, sqs`. `<service>/cmd/main.go` is the long-running variant used by the Docker images and Helm.

### Services and ports (minikube)

Services are ClusterIP-reachable by name inside the cluster (`authentication`, `bookings`, `journal`, `event-ledger`, `ui`, all on :8080 except the UI on :80; the UI nginx proxies `/api/v1/*` to them). On the host only what `task minikube:port-forward` exposes is reachable:

| Target | Host port | Notes |
|---|---|---|
| ui | 3000 | nginx image |
| postgres | 54320 | one instance, database `bilcool`, schema + role per service |
| localstack | 4566 | SNS, SQS, DynamoDB |

### Databases

- **Local (minikube/Helm):** ONE PostgreSQL 18 instance, database `bilcool`, one schema and login role per service (same shape as production), with `wal_level=logical` so `OUTBOX_MODE=replication` stays testable. Created by `infrastructure/helm/bilcool/files/db-init.sh`.
- **Production:** **one** Frostmoln PostgreSQL database `bilcool`, with **one schema per service** (`bookings`, `authentication`, `journal`). Each service has its own login role whose default `search_path` is `<service>, public`, so every connection, including dbmate and the outbox, lands in the service's own schema. The Go code is schema-agnostic. Never schema-qualify table names and never `SET search_path` in code or migrations. Tables such as `users`, `positions`, `inbox` and `outbox` exist in several schemas on purpose.
  - Connections use `sslmode=require` (the certificate is self-signed, so `verify-full` does not work) through a public Layer-4 load balancer; there is no connection pooler, so do not use `pgbouncer=true`.
  - The Lambdas keep few connections (`MaxOpenConns=2`, no idle) because Postgres has no pooler in front.
  - The database, schemas and roles are created by `infrastructure/frostmoln/bootstrap/bootstrap.sh`, not by Terraform or the service migrations. See `infrastructure/frostmoln/README.md`.
  - The old Neon setup is retired and its Terraform module and provider are removed.

### Service package layout

The layout below is followed fully by **bookings** and **authentication**:

```
<service>/
  cmd/main.go                               # Long-running entrypoint
  cmd/lambda/{http,sqs,outbox,migrate}/     # Lambda entrypoints (see above for which exist)
  internal/pkg/config/                      # Config loading (env vars)
  internal/pkg/domain/                      # Domain types, business logic, repository interfaces
  internal/pkg/application/                 # Use-case layer
  internal/pkg/application/commands/        # Command handlers (writes)
  internal/pkg/application/queries/         # Query handlers (reads)
  internal/pkg/persistance/postgresql/      # Postgres implementations + DbActions interface
  internal/pkg/event_dispatcher/            # SNS outbox dispatcher
  internal/pkg/web/                         # Gin HTTP router, handlers, Swagger annotations
  internal/migrations/                      # dbmate SQL migration files
  pkg/domain/                               # Public domain types (exported for other modules)
```

Differences: bookings also has `internal/pkg/inbox` (SQS consumer) and `internal/pkg/infrastructure/mapbox`; authentication also has `internal/pkg/mail/{brevo,ses}`. **journal** has only config, inbox, `persistance/postgres` (note the spelling) and web, with no CQRS layer. **event_ledger** has config, domain, inbox, `persistance/dynamodb` and web.

### Application layer (CQRS pattern, bookings and authentication)

The `application` package defines an `App` interface composed of `Commands` and `Queries` interfaces. The concrete `Application` struct embeds command and query handler structs:

```go
// application.go — interface composition
type App interface {
    Commands
    Queries
}

// New wires domain -> handlers -> application (bookings: New(repo); authentication also takes the mail sender, WebAuthn and the JWT secret)
func New(repo domain.BookingsRepository) *Application { ... }
```

Handlers live in `commands/` and `queries/` sub-packages. The web layer receives the `Commands` and `Queries` interfaces (not `App`), keeping routing decoupled from the application layer.

### Domain types pattern

Domain types in `domain/` define request/response structs with `json` and `validate` struct tags. Persistence implementations in `persistance/postgresql/` accept the `DbActions` interface rather than a concrete `*sql.DB`:

```go
// db_actions.go
type DbActions interface {
    QueryContext(ctx context.Context, query string, args ...any) (*sql.Rows, error)
    QueryRowContext(ctx context.Context, query string, args ...any) *sql.Row
    ExecContext(ctx context.Context, query string, args ...any) (sql.Result, error)
}

type Transactioner interface {
    BeginTx(ctx context.Context, opts *sql.TxOptions) (*sql.Tx, error)
}
```

This keeps the persistence layer decoupled from the concrete driver and makes it easy to pass `*sql.Tx` for transactional operations.

### Event-driven architecture (outbox pattern)

Services publish events using the **transactional outbox pattern**:

1. **Write**: A command handler writes domain data and an outbox record atomically in one DB transaction.
2. **Relay** (`OUTBOX_MODE`):
   - `polling` (production Lambda, Helm default): a scheduled job reads unsent rows (`emitted_at IS NULL`) from the `outbox` table. In production this runs every 10 minutes, so an event can take up to 10 minutes to arrive.
   - `replication` (the default when `OUTBOX_MODE` is unset in bookings and authentication; the Helm chart defaults to `polling`, `--set config.outboxMode=replication` tries it in dev; polling vs replication is not decided yet, both stay supported): the `message_broker` module tails the outbox table with PostgreSQL logical replication (`pgoutput`) through a replication slot. This needs `wal_level=logical`; the Frostmoln provider cannot apply parameter groups, so production uses `polling`.
3. **Publish**: the relay publishes the event to an SNS topic (LocalStack locally, AWS in production).
4. **Consume**: bookings, journal and event_ledger consume SQS queues subscribed to the topics. Consumers are idempotent (an `inbox` table, `ON CONFLICT DO NOTHING`).

`message_broker/` is the shared library that implements this. It is not a running service. Its own migration table is `outbox_schema_migrations`; `CreateTable` runs it on cold start of the bookings and authentication HTTP Lambdas.

```
bookings / authentication
  -> [outbox table]
  -> poller (Lambda, scheduled) or pg logical replication -> SNS topic
                                                  |
                                            SQS queue(s)
                                                  |
                                  bookings (users) / journal / event_ledger consumers
```

Example consequence: `bookings.users` is filled only by the `user.created` event from authentication, so a user who signs up and immediately books can get `404 user not found` until the event has been relayed.

### Authentication details

The `authentication` service implements:
- **JWT**: issued on login and validated by middleware on its protected routes. `JWT_SECRET` is read only by this service. The bookings router has no JWT middleware; `user_ref` comes from the request body.
- **WebAuthn/Passkeys**: `go-webauthn`; begin/verify/complete flow.
- **Email**: sent through **Brevo** (`internal/pkg/mail/brevo`, wired in both the long-running service and the Lambda). An SES sender exists in `internal/pkg/mail/ses` but is not wired in or selectable by config.
- **Roles**: role-based access control stored in the `roles` table.

### Event Ledger details

The `event_ledger` service consumes events from SQS and stores them in **DynamoDB**. It exposes a REST API with Gin and Prometheus metrics at `/metrics`, and uses Ginkgo/Gomega for tests.

## Testing conventions

### Build tags

Integration tests require real infrastructure (databases, AWS services via testcontainers or LocalStack). They are gated with a build tag:

```go
//go:build integration
```

Run unit tests only: `go test ./...`
Run integration tests: `go test -tags=integration ./...`

### Mock generation

Mocks are generated with `mockgen` (`go.uber.org/mock`) from `//go:generate` directives. They are gitignored (`**/*_mock.go`), so generate them locally with `go generate ./...` in a module directory before running tests; CI does this as part of `task <service>:test`. Two older mocks under `bookings/` are tracked by accident; do not rely on that.

### Shared test helpers (`testing/` module)

The `testing/testdb` package provides:
- `SuiteDbIntegration`, created with `SetupDatabase(t, embeddedMigrationsFS, dbName)`: starts a PostgreSQL container via testcontainers and runs the dbmate migrations. Clean up with `TearDown(t)`.
- `migrate.go`: the programmatic dbmate runner.

`testing/aws/local_cloud.go` provides the LocalStack helper.

Import path: `github.com/arngrimur/bilcool_monolith/testing/testdb`

## HTTP layer conventions

- **Framework**: Gin v1.12
- **Swagger**: annotations in `web/router.go` and domain types; regenerate with `task swagger` (bookings and event_ledger). Check handlers against the real route: the bookings create-booking route is `PUT /api/v1/bookings`, although its swagger annotation says `POST`.
- **Graceful shutdown**: all services listen for `SIGINT`/`SIGTERM` and drain on shutdown (30 seconds in bookings)
- **Route groups** (bookings router): `queryRoutes` (GET), `commandRoutes` (PUT/POST/DELETE), `internalRoutes` (`/swagger/*`); `/ping` is registered on the engine. Authentication uses an admin group with JWT and admin middleware instead.
- **Error handling**: use `NewHttpError(err)` to map domain errors to HTTP status codes (bookings, authentication, event_ledger); never return raw errors. A missing user is `404`.

## Environment variables

Config is read from the process environment by each service's `internal/pkg/config` package. There is no `.env` loading in the Go code; Helm and Terraform set the variables.

| Variable | Services | Description |
|---|---|---|
| `DATABASE_URL` | bookings, authentication, journal | Postgres connection string. Production: `postgres://<service>:<pw>@<host>:5432/bilcool?sslmode=require` |
| `OUTBOX_MODE` | bookings, authentication | `polling` or `replication` (default `replication` when unset) |
| `RELEASE` | all Gin services | Any value switches Gin to release mode |
| `API_PORT` | journal, event_ledger | Listen address, default `:8080` |
| `JWT_SECRET` | authentication | JWT signing secret (required) |
| `FROM_EMAIL` | authentication | Sender address (required) |
| `MAIL_SENDER` | authentication | `brevo` (default) or `log` (development only: login code is logged, not mailed) |
| `BREVO_API_KEY` | authentication | Brevo transactional email API key (required unless `MAIL_SENDER=log`) |
| `WEBAUTHN_DISPLAY_NAME` | authentication | WebAuthn relying party display name (required) |
| `WEBAUTHN_RP_ID` | authentication | WebAuthn RP ID (required, e.g. `localhost` or `bilcool.areskiftet44.se`) |
| `WEBAUTHN_RP_ORIGINS` | authentication | Allowed origins, comma separated (required) |
| `MAPBOX_ACCESS_TOKEN` | bookings | Optional; used to compute distance when a booking ends |
| `DYNAMO_TABLE_NAME` | event_ledger | DynamoDB table name (required) |
| `AWS_REGION`, `AWS_ENDPOINT_URL`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | AWS SDK | Read by the AWS SDK. Locally use `test` credentials and `http://localhost:4566` (LocalStack); production uses `eu-north-1` |

## CI/CD (.github/workflows/)

`build.yml` (push and pull request):

1. **vendor** (`task vendor`, cached), **lint**, **build-testing**, **build-bilcool-lib**
2. **build-message-broker**: build + unit + integration tests
3. **build-bookings / build-authentication / build-event-ledger / build-journal**: depend on message-broker, testing and bilcool-lib
4. **lambda-build**: builds all Lambda zips
5. **build-ui**: `npm ci`, build and tests (independent)

Pull requests also run **terraform-plan** (`init -backend=false` + `validate` only; it does not plan against real state).

Deploys:
- **Push to `main`**: `lambda-deploy` (uploads zips to S3, updates the 12 Lambda functions, invokes the three migrate Lambdas) and `ui-deploy` (S3 sync with `--delete` + CloudFront invalidation). Merging to `main` is a production deploy.
- **Tags**: also build and push the Docker images (`docker-build-*`, `docker-push*`) and re-run `lambda-deploy`. `helm-deploy-frostmoln` only runs when the repository variable `DEPLOY_FROSTMOLN_K8S` is `true` (the apps run on Lambda for now).

`fetch-logs.yml` (manual) fetches CloudWatch logs for a Lambda function.

## Key conventions for AI assistants

- **Go version**: This project uses **Go 1.26**.
- **Pointer to primitive**: Never write helper functions (`strPtr`, `intPtr`, `boolPtr`, etc.) to create pointers to primitive values. Declare a named variable and take its address: `s := "value"; req.Field = &s`.
- **Service isolation**: Never import a service's `internal/` packages from another service. Only types under `<service>/pkg/` are public.
- **Persistence interface**: Repository implementations accept `DbActions`, not `*sql.DB`. When adding new repository methods keep this pattern.
- **CQRS split**: In bookings and authentication, new use cases go into `commands/` (writes) or `queries/` (reads) sub-packages, not directly in `application.go`.
- **Error mapping**: Add new domain error types to the `NewHttpError` mapper in the `web` package; do not add HTTP logic to the domain or application layer.
- **Migrations**: Always create a new timestamped migration file; never modify an existing one. Keep SQL schema-agnostic (no schema-qualified names, no `SET search_path`): in production each service's role puts it in its own schema.
- **go generate**: Mocks are generated locally and gitignored. After changing an interface, run `go generate ./...` before testing.
- **Outbox events**: Domain state changes that need to notify other services must go through the outbox table; never call SNS/SQS directly from a command handler.
- **Secrets**: never read, print or commit `.envrc`, `*.tfvars` or `db-credentials.env`.
